# AccountNav

## 1. Purpose

Give public visitors a way to sign in or create an account, and signed-in people a way to sign out, on every public page. Sources: accounts UI/UX (header `AccountNav`).

## 2. When to use

Use it as the header of the `(marketing)` and `(auth)` layouts. Sources: accounts UI/UX.

## 3. When not to use

Panel screens use PanelShell with their own header actions. Do not show the user's name: the cookie hint carries none. Sources: accounts UI/UX; platform F8.

## 4. Anatomy

The brand link and a named `nav`. When signed out, the nav holds “Sign in” (a quieter link) and “Create account” (filled, the main action). When signed in, it holds the app's sign-out control. Sources: accounts UI/UX; reference R01.5.

## 5. Variants

There are no visual variants; the state comes from `signedIn`. Sources: package API.

## 6. States

- **Signed out.**
- **Signed in:** an optimistic hint from the cookie's presence, never an authorization.
- **Sign-out failed:** the app shows feedback next to its control and allows a retry, without claiming the session ended.

The links have focus and hover states. Sources: accounts UI/UX.

<Unstyled><Canvas of={Stories.SignOutFailed} /></Unstyled>

## 7. Behavior and accessibility

It is a `header` (banner landmark) with a named `nav`. Tab order is brand, then sign-in, then create account. The filled link is at least 36 px high with the standard focus ring. It is server-safe; the only client JS is the app's sign-out control. Sources: WCAG 2.4.3, 2.4.7, 2.5.8.

## 8. Content

Use verb phrases: “Sign in”, “Create account”, “Sign out”. All text comes through props. Sources: accounts UI/UX; task Content.

## 9. Responsiveness

At 320 px the brand and nav wrap onto two lines. Sources: WCAG 1.4.10.

## 11. Code

