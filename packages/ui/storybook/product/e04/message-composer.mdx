# MessageComposer

**Preliminary.** E04 has no screen specification. Points marked **Proposal** wait for your decision or the E04 spec.

## 1. Purpose

Let a participant write and send one message during the session, optionally as a reply to a specific message, without losing the text if sending fails. Sources: E04-S01; R02.2; task form rules.

## 2. When to use

The session room while the session is in progress, for both the mentee and the mentor. Sources: E04-S01; R01.

## 3. When not to use

- Before the start and after the end: show a notice instead, and no field. Sources: R01; R02 (an ended transcript is read-only, user decision 2026-11-01).
- For the question before payment: use CrudForm on the new-booking screen (E02).
- For long forms with several fields: use CrudForm.

## 4. Anatomy

- An optional reply preview: “Replying to …”, an excerpt, and “Cancel reply”.
- A labelled Textarea (FormField, Required) with a hint.
- A failure line with `role="alert"`.
- The Send button (primary).

Sources: approved Q5; FormField anatomy; R01.5 (one primary action).

## 5. Variants

## 6. States

- **Empty send:** the field is marked invalid, “Write a message first” is announced, and focus returns to the field.
- **Sending:** the button reads “Sending…”, `aria-busy`. A second send is ignored. The field is read-only, and its text stays.
- **Failed:** the server's message is announced, and the text stays. The field is not marked invalid, because the text is not wrong.
- **Sent:** the field clears and keeps focus. The message appears in the conversation from the server's response.

The button is never disabled without a reason: an empty send explains itself. Hover, focus and pressed states are those of Textarea and Button. Sources: task form rules (duplicate guard, input preserved, success only after confirmation); WCAG 3.3.1, 4.1.3.

## 7. Behavior and accessibility

- **Enter** adds a line, because pasted code needs line breaks. **Ctrl+Enter** or **Cmd+Enter** sends (user decision 2026-11-01; the hint says so).
- Choosing Reply on a message moves focus to the field, and the field's description starts with “Replying to …”.
- **Cancel reply** returns focus to the field.
- A reply set on the first render does not take focus, so a page never jumps on load.
- The failure line is `role="alert"` and linked through `aria-describedby`.

Sources: WCAG 2.1.1, 2.4.3, 3.3.1; approved Q5; found while writing the docs (focus on mount moved the docs page).

## 8. Content

- **Label:** “Your message”.
- **Hint:** how to paste code and how to send.
- **Button:** “Send”, and “Sending…” while pending.
- **Errors:** what happened and what to do, for example “The session ended at 18:50, so this message was not sent. Your text is still in the field.”
- **Reply heading:** “Replying to Alex”.

Longer languages wrap the hint and the reply preview, never the button label. Sources: U01.1; task Content rules.

## 9. Responsiveness

At 320 px the reply preview stacks above “Cancel reply”, and the field takes the full width. Sources: approved Q3; WCAG 1.4.10.

## 11. Code

```tsx
<MessageComposer label="Twoja wiadomość" description="Kod wklej między liniami z trzema znakami ```. Ctrl+Enter wysyła."
  sendLabel="Wyślij" pendingLabel="Wysyłanie…" emptyError="Najpierw napisz wiadomość"
  replyTo={replyTo && { id: replyTo.id, heading: `Odpowiedź do: ${replyTo.author.displayName}`, excerpt: excerpt(replyTo.body), cancelLabel: 'Anuluj odpowiedź', onCancel: () => setReplyTo(undefined) }}
  onSend={(body) => apiCall(`/api/bookings/${booking.id}/messages`, { method: 'POST', body: { body, replyToId: replyTo?.id ?? null } })}
  onSent={(message) => { append(message); setReplyTo(undefined); }} />
```

Sources: user decision 2026-11-01 (endpoint).
