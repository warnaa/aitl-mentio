# Button

## 1. Purpose

Run an action on the current task, such as saving a mentor page or confirming a booking. Source: R01.5; E01/E02 UI/UX.

## 2. When to use

Use a primary button for the next task action: save the draft, continue to payment or pay the displayed price. Use a quieter button for preview, edit or cancel. An action that removes availability uses the destructive treatment after its confirmation step. Sources: R01.5; E01 mentor editor/availability; E02 booking/payment; platform F5.

## 3. When not to use

For ordinary navigation, use Link. A navigation action that needs button emphasis may use `asChild` with an anchor: it must still expose link semantics. Do not use a button to disguise a link or a clickable div to replace a button. Sources: WAI-ARIA button pattern; task implementation anti-patterns; R01.5.

## 4. Anatomy

Required: the visible action label, or an accessible name for an icon-only control. Optional: a leading or trailing Lucide icon, disabled explanation and adjacent action error/status. Decorative icons have `aria-hidden`. The hit target includes the whole control. Sources: task stage 2; WCAG 1.1.1, 2.5.8, 4.1.2; approved Q2.

## 6. States

Default, hover, focus and pressed keep the action recognizable. Hover/focus/pressed samples below freeze the same declarations used for real pseudo-classes through documentation-only `data-preview-state`. A selected toggle uses `aria-pressed`; ordinary one-time actions do not. Sources: task state-matrix requirement; WAI-ARIA button pattern.

Disabled means the action cannot run: provide a visible reason near it and connect that reason with `aria-describedby`. A disabled control is skipped by normal Tab navigation, so the explanation must be readable independently. Loading uses `disabled`, `aria-busy` and a truthful progress label; show success only after server confirmation. An action failure remains in adjacent alert text and preserves the task context. Sources: task disabled/loading/error requirements; platform F5; E01 dirty/publish states; E02 payment states; R02.4. There is no custom loading prop or automatic request handling in Button.

## 7. Behavior and accessibility

Native buttons activate with Enter and Space; mouse/touch activation calls the same handler. Use `type="button"` for standalone actions inside forms and `type="submit"` only for the intended submitter. Preserve DOM order as keyboard order, visible full-color focus and its neutral offset. Screen readers hear the accessible name, button role and relevant disabled/pressed/busy state. Sources: native button contract; WAI-ARIA button pattern; WCAG 2.1.1, 2.4.3, 2.4.7; approved contrast correction.

`asChild` delegates to exactly one semantic child; it does not make an anchor disabled or provide button keyboard behavior to an arbitrary element. Use an anchor with a real destination for navigation; do not pass native button-only props to that anchor. Source: retained Radix Slot contract and task semantic-element rule.

## 8. Content

Use a verb and object: “Save mentor page”, “Remove availability” or “Pay 120 PLN”. Avoid “OK” for irreversible confirmation and ambiguous icon-only labels. The tone is direct and friendly. Sources: U01.1; task Content; E02 payment UI.

No label character maximum is enforced by this API or approved material. Keep the label specific; when a translation grows, allow wrapping instead of clipping the object or silently adding an unapproved smaller text size. Price and duration must come from the screen's actual data; examples do not establish a rate. Sources: approved Q2/Q3; task long-content/translation requirement; R03/R08.

## 9. Responsiveness

Check the real control at 320, 768 and 1440px. Long labels must remain readable at 320px, icon buttons keep their named target, and controls may wrap as a group without changing reading order. The target remains at least 24 × 24px. Sources: approved Q3; task stage 2; WCAG 1.4.10, 2.5.8.

## 11. Code

Minimal action:

```tsx
import { Button } from '@mentio/ui/components/button';
<Button type="button" onClick={saveDraft}>Save mentor page</Button>
```

Typical pending publication action, with its reason readable outside the control:

```tsx
<Button type="button" disabled={saving} aria-busy={saving}
  aria-describedby="publication-status" onClick={publishSavedDraft}>
  {saving ? 'Publishing page…' : 'Publish mentor page'}
</Button>
<p id="publication-status" role="status">
  {saving ? 'Publishing your saved draft.' : 'Save draft changes before publishing.'}
</p>
```

The caller owns the request, synchronous duplicate guard and server result; Button does not perform the mutation. Source: E01 editor/publish contract; platform F5; R02.4.

## 12. Good and bad

Good: “Remove availability” names the destructive action. Bad: “OK” requires the user to reconstruct its meaning from surrounding text. The paired specimen keeps the bad wording explanatory rather than introducing an active inaccessible control. Sources: task confirmation/content requirements; E01 availability.
