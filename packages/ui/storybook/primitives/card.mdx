# Card

## 1. Purpose

Group the information and actions that belong to one object or one editing section on an opaque, bounded surface. Sources: reference R01.4 and A01.2 (opaque warm surfaces); approved token table (`--card`).

## 2. When to use

Use it for the booking summary before payment (mentor, time, length, price, “Pay”). Use it for a section of the mentor page editor such as “Public work”. Use it for the existing admin overview metrics. Sources: book-and-pay UI/UX; mentor-pages UI/UX; existing `/admin` page.

## 3. When not to use

Do not wrap each row of a dense list in a card. Mentor and session lists use rows with thin separators. Do not nest a card in a card: separate inner groups with spacing or a Separator. Do not use a card as a button. Put a Link or Button inside instead. Do not use it for page-level feedback: the Alert and ErrorMessage components cover that. Sources: references R01.1 and R01.3; task What to avoid (card in card); WCAG 4.1.2.

## 4. Anatomy

`Card` is the surface: 1 px border, 14 px radius, card role background, 24 px vertical padding and 24 px between parts. `CardHeader` holds `CardTitle` in the section role (20/28 semibold), and optionally `CardDescription` (14/20, muted) and `CardAction` (top-right, for example “Edit question or length”). `CardContent` and `CardFooter` (actions; it wraps) are optional. Adding the `border-t` class to the footer, or `border-b` to the header, adds the matching 24 px padding. Sources: package API; tokens (radii and shadows retained, `--space-panel`); user decision 2026-10-31 (CardTitle section role); reference R01.5.

`CardTitle` renders a `div`. Put a heading element inside it, at the level that fits the page, so the title appears in heading navigation. Sources: WCAG 1.3.1, 2.4.6.

## 5. Variants

One surface. A metric card is a composition, not a variant: the description first, then a title with `tabular-nums`. Sources: package API; approved stage-0 Q2 (numbers tabular).

## 6. States

A card is static. Hover, focus, pressed, selected and disabled are not card states, and its interactive children keep their own states. Loading: set `aria-busy` on the card and keep the last saved content visible with a status line. Skeleton shapes arrive in batch 4. Error: the surface stays neutral and a linked message near the cause says what happened and what to do. Sources: task stage 2; references R02.4 and U02.1 (local feedback); WCAG 4.1.3.

## 7. Behavior and accessibility

There is no keyboard behavior of its own. Focus order follows source order: the header action, then content, then footer actions. The primary action goes in the footer, after the information it confirms. Use a real heading inside `CardTitle`. Do not add a click handler to the surface. The card's border (border role, 1 px) separates it in both themes, so the shadow is never the only separator. Sources: WCAG 1.3.1, 1.4.11, 2.4.3; task What to avoid (shadow as the only separator); reference R01.5.

## 8. Content

Write the title as the object or section name: “Booking summary”, “Public work”. Write the description as one supporting sentence with the date and time in Warsaw time. Long titles wrap and do not truncate. Code and filenames in content use the monospace role and may break anywhere. Write prices as whole amounts with “zł” after the number, for example “240 zł”. Sources: U01.1; reference R01.2; D10. Date, time and price formats in examples: user decision 2026-10-31 (“6 November 2026 at 18:00 (Warsaw time)”, “240 zł”); final wording on the Content page, stage 4.

## 9. Responsiveness

At 320 px the card fills the column. The header action stays top-right, and long titles wrap beside it. Footer buttons wrap onto new lines. At 768 and 1440 px place cards in the content column up to 1152 px. Do not stretch a reading card wider than its text needs. Sources: approved stage-0 Q3; WCAG 1.4.10.

## 11. Code

Minimal:

```tsx
import { Card, CardContent, CardDescription, CardHeader, CardTitle } from '@mentio/ui/components/card';
<Card>
  <CardHeader><CardTitle><h2>Booking summary</h2></CardTitle>
    <CardDescription>Text session with Alex, 6 November 2026 at 18:00 (Warsaw time).</CardDescription></CardHeader>
  <CardContent><p>50 minutes — 240 zł</p></CardContent>
</Card>
```

Product composition:

```tsx
<Card>
  <CardHeader>…<CardAction><Button variant="ghost" size="sm">Edit question or length</Button></CardAction></CardHeader>
  <CardContent><p>50 minutes — 240 zł</p><p>Simulated payment — no money is charged.</p></CardContent>
  <CardFooter className="border-t"><Button>Pay 240 zł</Button></CardFooter>
</Card>
```

Sources: book-and-pay UI/UX (summary, simulated payment notice, edit action).
