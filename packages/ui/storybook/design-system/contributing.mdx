## What a new component needs

- A docs page with all 13 sections (purpose, when, when not, anatomy, variants, states, behaviour and accessibility, content, responsiveness, API, code, good and bad, related), each rule with its source. Write **Proposal** where there is no source, and report it. Sources: task stage 2; task rule 4.
- Stories:
  - Playground with controls;
  - every variant and size;
  - a state matrix, with hover and focus frozen through `data-preview-state`;
  - long content and narrow;
  - a play function for its main behaviour.

  Source: task stage 2.
- No story-only copies of components; real package components only. Source: task rule 5.
- Unit tests with 100% coverage, and a regression test for every bug. Source: AGENTS.md (Testing).
- An entry in `storybook/design-system/inventory.ts`, then `npm run docs:agent` to update the table in `docs/design-system.md` (`npm run check:agent-doc` fails when it is stale). Source: this site.
- Ids from `useId`, one landmark per page-level component, and no landmark per repeated item. Source: verification 2026-11-01.

## Changing a token

1. Change the raw value or the semantic alias in `src/styles/globals.css`, keeping the source comment. Sources: task stage 1; tokeny.md.
2. Recalculate contrast for every pair in both themes; stop and ask if a pair drops below 4.5:1 (text) or 3:1 (interface). Sources: task stage 1; WCAG 1.4.3, 1.4.11.
3. Run every story in both themes, the built-page checks, and check `/admin` in both themes: global CSS reaches the app. Source: approved stage-0 plan.

## Who approves

Damian approves everything: he owns the design system as well as the product (user decision 2026-11-01). That covers:
- new components, variants and tokens;
- changes to approved decisions;
- product rules (R, D and N in the brief), through a superseding row in the brief.

Until approved, write **Proposal** in the docs.
