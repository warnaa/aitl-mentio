- 2026-11-03 — **Validate a redirect target *after* normalisation, not only before.** `safeReturnTo` refused a leading `//` on the raw input, then returned the URL parser's normalised path, and dot segments or backslashes (`/foo/..//evil.example`, `/%2e%2e//evil.example`, `/.//evil.example`, `/foo/..\\evil.example`) collapse into `//evil.example`, a protocol-relative off-site URL. The OAuth callback re-validated and so refused it, which is why it was not exploitable yet. Fix: also refuse a normalised pathname starting with `//`, and test that the output is a fixed point (`safeReturnTo(safeReturnTo(x)) === safeReturnTo(x)`).

- 2026-11-03 — **`em.nativeUpdate` bypasses MikroORM's identity map, so the same scope keeps reading the pre-write row; and an incomplete stub row hides it.** `grantRole` then `revokeRole` in one scope: the revoke's `findOne` got the cached entity with the old roles and `sessionVersion`, missed its own precondition and the role stayed. `endAllSessions` twice bumped once. Found in review (Codex), not by tests, because the fake EM's `nativeUpdate` mutated the very object `findOne` returned. Fix: every version-guarded user write goes through `updateUserAtVersion` (`services/auth/user-version.ts`): conditional `nativeUpdate`, then `em.refresh(user)` (re-hydrates the same instance *and* its `__originalEntityData`, so nothing turns dirty), on a hit and a miss. `user-version.test.ts` pins this on **real** MikroORM with only the driver stubbed. Trap met on the way: MikroORM's `shouldRefresh` re-queries whenever a comparable column was never loaded, so a stub row missing `githubId` etc. made every `findOne` hit the driver and the bug vanished; the test now asserts a repeat `findOne` is served from the identity map. Confirmed against PostgreSQL in a scratch database, with and without the fix.

- 2026-11-03 — **A guarded layout keeps deep links only through a `proxy.ts` request header; the proxy is not an auth boundary.** Next gives a layout no pathname and lets its `redirect()` win over the page's, so `/admin/users` signed out used to return to `/admin`. `packages/app/src/proxy.ts` now overwrites `x-devmentor-path` with `pathname + search` on `/admin`, `/home` and `/mentor` (forwarded with `NextResponse.next({ request: { headers } })` — passing `headers` at the top level would send them to the *client*), and the guards read it through `safeReturnTo`, falling back to their literal path. The proxy never reads the session or refuses anything: enforcement stays in the guards and services, which must hold if the matcher drifts. Add a new signed-in surface to the proxy `matcher` or its deep links fall back to the section root. Unit-test a proxy by calling it with a real `NextRequest` and reading `x-middleware-request-<name>` off the response.

- 2026-11-03 — **A Next route-group path in `coverage.include` is silently dropped unless its parentheses are escaped.** The entries are picomatch globs, so `'packages/app/src/app/(auth)/sign-in/page.tsx'` reads `(auth)` as a group matching `auth` and matches no file; the gate then stays green without measuring the page at all (the per-file 100% threshold only applies to files it found). Write `'packages/app/src/app/\\(auth\\)/sign-in/page.tsx'` in the config source and confirm the file appears in `coverage/unit/coverage-final.json`. Related, from the same change: a guarded **layout** cannot see the path, and Next lets its redirect win over the page's, so a signed-out visit to `/admin/users` returns to `/admin` after sign-in, not to `/admin/users`. Keeping deep links needs the path from a `proxy.ts` request header; nothing does that yet.

- 2026-11-02 — **A signed token with no random claim is predictable, so the OAuth state cookie check meant nothing.** `TokenService.signPurposeToken` signed only `aud`, `sub`, `iat` and `exp`. Two calls with the same purpose and subject in the same second produced the *same* JWT, so an attacker could call `/api/auth/github` at the moment a victim did, get the exact `state` the victim's cookie held, and pass the callback's equality check with their own GitHub `code` (login CSRF). It came out when a unit test showing "attacker state ≠ victim cookie" was redirected to `/home`. Fix: every purpose token carries `jti: crypto.randomUUID()`, with a regression test that two tokens minted from identical input at the same instant differ. Any token whose *equality* is a security check needs its own entropy; an HMAC over predictable claims gives none.

- 2026-11-02 — **A find-or-create race has a third outcome besides "lost on the unique constraint": the winner commits *between* your lookups.** `UserService.findOrCreateFromGithub` looks up by `github_id`, then by verified email. Against real PostgreSQL (six concurrent first sign-ins), a loser's `github_id` lookup missed, the winner committed, and the email lookup then found a verified row *already carrying this same `github_id`* — which the first draft treated as "linked to another GitHub account" and refused with a 409. The mocked-em unit race passed because its barrier held both callers before the first lookup. Fix: a matching `github_id` on the email branch is the winner, not a conflict; only a *different* id refuses. Verify race handling against a real database (scratch DB, forked ems, a barrier on `flush` to force the constraint path) — a fake em only exercises the interleaving you thought of. Related: an opportunistic write inside `loadSession` uses a conditional `em.nativeUpdate` (precondition `session_version`), never `em.flush()`, because the session resolves lazily mid-service and a flush would commit that service's half-built unit of work.

- 2026-11-02 — **Never cache a rejected promise as a process-wide singleton.** `getContainer` cached `build()`'s promise on `globalThis`, so when the first request hit a down database (`getOrm` rejects) every later request got the same rejection until a restart — the very failure `getOrm` avoids by not caching a failed connection. It now clears the cache when the build rejects (only if the cache still holds that same promise), so concurrent callers still share one in-flight build. A related trap with awilix-scoped async values: a cached `Promise` that a constructor resolves but never awaits becomes an unhandled rejection when it fails, so the scoped `session` attaches a no-op `catch` while awaiters still see the rejection.

- 2026-11-02 — **A PostgreSQL `text[]` in MikroORM v7 is `p.array()` (spiked on 7.1.14).** `p.array()` maps to `ArrayType`, whose Postgres declaration is `text[]` and which hydrates to a real JS `string[]` (`$contains` works); `.default(['mentee'])` emits `default '{mentee}'`, and `p.type('text[]')` is an equivalent spelling. A property-level `.check('…')` is generated as `"<table>_<column>_check"`, recorded in the snapshot, and **lifted by discovery into `meta.checks`** — `meta.properties.roles.check` is `undefined` afterwards, so assert on `checks`. A Postgres `CHECK` passes on `NULL`, so guard array shape with `cardinality(x) > 0` (not `array_ndims`, which is `NULL` for `'{}'`) and reject null members with `array_position(x, null) is null`. Two traps met on the way: the migrations glob has the same colocated-test trap as the seeder glob (now `!(*.d|*.test).{js,ts,cjs}` in `config.ts`), and `config.ts` names the snapshot `devmentor` (→ `migrations/devmentor.json`) while the committed file is `.snapshot-devmentor.json` — run `db:migration:create` with `MIKRO_ORM_MIGRATIONS_SNAPSHOT_NAME=.snapshot-devmentor` (as the integration harness does), or it ignores the committed snapshot, diffs against the live database instead, and writes a stray `devmentor.json`.

- 2026-11-02 — **The React test toolchain now exists; the 2026-09-04 "no jsdom / no Testing Library" constraint is resolved.** `jsdom`, `@testing-library/react`, `@testing-library/user-event` and `@vitejs/plugin-react` are pinned root devDependencies; Node stays the default environment and client-component tests opt in with `// @vitest-environment jsdom`. `user-event` had been resolving through Storybook's hoisted copy without being declared — declare every test dependency you import. The approach is in `AGENTS.md` (Testing requirements).

- 2026-11-02 — **`npm run test:integration` had never run on Windows; CI is Linux-only, so four POSIX assumptions went unnoticed.** (1) Node refuses to spawn `npm.cmd` without a shell (`EINVAL`, CVE-2024-27980) and deprecates passing an argument array alongside `shell` (DEP0190), so `global-setup.ts` passes one command string on Windows. (2) `NODE_ENV=production next build` is POSIX shell syntax, so the app's `build`/`start` scripts use `cross-env`. (3) Windows has no process groups, so killing the npm wrapper orphaned the Next.js server; the harness ends the whole tree with `taskkill /T /F`. (4) agent-browser's daemon inherits the CLI's stdout and keeps the pipe open after the CLI exits, so `execFile` hung until its timeout; `runAgentBrowser` writes output to files under `test-results/integration/agent-browser/` and completes on the CLI's exit.

- 2026-11-02 — **A child that kills itself (`process.kill(process.pid)`) exits with code 1 on Windows, not by signal.** Only POSIX reports `code === null` plus a signal, so tests built that way fail on Windows and leave the `code ?? …` branch uncovered. To test a signal exit portably, have the *parent* call `child.kill('SIGTERM')`: Node reports `(null, 'SIGTERM')` on every platform. `scripts/{setup,storybook}/effects.test.mjs` get the real child through a pass-through `vi.mock('node:child_process')` wrapper that records each spawned child.

- 2026-11-02 — **Issue numbers in this repo are not the upstream `open-mercato/ai_techleaders_project` numbers.** The after-lesson-03 issues were imported into `warnaa/aitl-mentio` as new issues #26–#55 (upstream #7–#34 → #26–#53, #36 → #54, #37 → #55), every `#N` and issue link in `.ai/`, Storybook and the prototype was remapped, and the earlier plan's #8–#25 were closed as not planned. `PR #N` references and `pull/`/`blob/` links still point at upstream PRs and files, and `edge case #N` is a spec table row, not an issue. The upstream restore script refuses any repo that already has issues or PRs, so a re-import needs its own importer.

- 2026-09-10 — **Storybook and esbuild treat any ancestor `.pnp.cjs` as Yarn Plug'n'Play configuration, even inside a nested npm project.** The symptom is valid Storybook imports failing with “The Yarn Plug'n'Play manifest forbids importing” after `npm ci`, while CI passes on a machine without the unrelated manifest. DevMentor's launcher runs the installed Storybook CLI from an isolated OS-temporary cache directory and supplies the real `.storybook` directory absolutely; do not delete or rewrite a developer's parent Yarn workspace to fix the npm project.
- 2026-09-08 — Three traps found while specifying E02 (`.ai/specs/2026-09-08-mentors-become-bookable.md`) that bite anyone touching roles, slots, or a MikroORM relation before its table exists. (1) **`grantRole` bumps `session_version`, so granting a role signs the caller out unless the route re-issues the cookie.** E01 puts `grantRole` on the closed list of `session_version` triggers; invitation acceptance (#34) is the first grant path, and a handler that commits the transaction without signing a fresh cookie leaves the user's own action invalidating their token — the redirect to `/mentor` then lands on sign-in. Only a route handler can set a cookie in the App Router, so this can never be fixed in a page or a service. (2) **A slot is a bare start instant but the *mentee* picks 25 or 50 minutes at booking (#36 + #40), so slots at 14:00 and 14:30 can double-book a mentor** — neither issue notices. The read-time filter is `viableLengths(slotStart, occupied, lengths)`; the guarantee is *not* a per-slot lock, which two concurrent bookings on two different slots sail straight through. Serialise on the **mentor** row (`SELECT … FOR UPDATE` on `mentor_profiles`) and back it with `EXCLUDE USING gist (mentor_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` on `bookings`. (3) **Never declare a MikroORM relation whose column does not exist yet.** A `Slot.booking` property with no `booking_id` column puts the column in every generated `SELECT` (so all reads of `slots` fail) and regenerates it on the next `db:migration:create` diff against the committed snapshot. Also note two boundaries that block the obvious implementation: `packages/db/**` may not import `@devmentor/core` (`eslint.config.mjs:44-48`), so a migration cannot call a vocabulary's `sqlValueList()` or a `uniqueSlug()` helper — hand-write the SQL and guard the drift with a `core`-side test that reads the migration file; and `SDLC.md:97` grades **any** schema migration `risk-high`, however small the feature.

- 2026-09-08 — **A "required in production" env check must not live in the zod schema.** `npm run build` forces `NODE_ENV=production`, the CI Build job sets no env at all, and `getEnv()` is reachable at build time from `admin/page.tsx` and the pino logger — so a schema refine that fails on a *missing* `SESSION_SECRET` in production would break every CI build. Put such checks at first container creation (`createContainer`), which only ever runs at request time. Schema-level refines are fine for *dangerous* combinations that are only ever set deliberately (e.g. `AUTH_IDENTITY_ADAPTER=mock` without `INTEGRATION_TEST_RUN=1`). Recorded in primitives spec B6.
- 2026-09-06 — **`npm run db:up` does not work in this sandbox — there is no Docker and no `psql`.** Neither `docker`, `docker compose`, nor any PostgreSQL client/server binary is on `PATH`, and there is no passwordless `sudo` to install one, so `docker-compose.yml` is unusable here. What *is* available is the sandbox's own PostgreSQL 17 on `127.0.0.1:5432` reachable as superuser `postgres`/`postgres` (the same server the injected `DATABASE_URL` points at, database `open-mercato`). To provision a fresh checkout: run `npm install` first (it brings in `pg` as a MikroORM transitive dep), then drive SQL through `node -e "const {Client}=require('pg') ..."` — `CREATE ROLE devmentor LOGIN PASSWORD 'devmentor' CREATEDB` and `CREATE DATABASE devmentor OWNER devmentor` — so the repo's documented `devmentor`/`devmentor` defaults still hold and `.env` stays consistent with `.env.example` and CI. Then `DATABASE_URL=postgres://devmentor:devmentor@127.0.0.1:5432/devmentor npm run db:migrate && ... npm run db:seed` (the explicit prefix is still required — see the 2026-09-04 entry below). Verify against `select current_database()`, not the CLI's `injected env` line, which lies.
- 2026-09-04 — Four constraints found while specifying E01 (`.ai/specs/2026-09-04-accounts-and-roles.md`) that will bite anyone adding UI, a scoped list, or admin chrome. (1) **There is no React test toolchain.** `vitest.config.mts` sets `environment: 'node'` and there is no `jsdom`, `@testing-library/react`, or `@vitejs/plugin-react` anywhere; no `*.test.tsx` exists. Any story adding `.tsx` must install and configure them first, or it cannot meet `AGENTS.md`'s 100%-per-file bar. Server components are testable by invoking the async function and asserting the returned element tree — no DOM needed; only client components need jsdom. (2) **`makeCrudRoute` cannot see the session.** `resolve` is `(cradle: Cradle) => CrudService` and `authorize` is `(req, cradle) => void | Promise<void>` — neither hands a `Session` to the service, so a per-caller-scoped list (`listForMentee`/`listForMentor`) cannot ride `makeCrudRoute` without changing `MakeCrudRouteOptions`/`CrudService`, both protected §2 exports. Also note `authorize: async (req) => requireRole(...)` does **not** typecheck (`requireRole` returns `Session`, not `void`) — use a braced body. (3) **The admin chrome is asserted behaviour, not free.** `tests/integration/admin.integration.test.ts:22` asserts `link "Users"`, which `BACKWARD_COMPATIBILITY.md` §7 names; replacing `admin/layout.tsx`'s sidebar must preserve an accessible `link "Users"` or update the test in the same PR. (4) `packages/db/src/entities/base.entity.ts` claims a "uuid v7 primary key (time-sortable)" but uses `crypto.randomUUID()`, which is **v4** — the comment is wrong, the ids are not sortable.
- 2026-09-04 — An OAuth **state** cookie must be `SameSite=Lax`, never `Strict`. The engineering-standards spec suggests "`lax` (or `strict` for auth-only routes)", and `Strict` looks like the safer read for an auth cookie — but the provider's callback is a cross-site top-level navigation, so a `Strict` cookie is not sent and *every* sign-in fails state validation. Related: `Response.redirect()` cannot carry `Set-Cookie`; build `new Response(null, { status: 302, headers })` when a redirect must also set the session cookie.

- 2026-09-04 — Sandbox `next dev` serving 500s on every route usually means the pm2 `workspace-preview` process is **stale**, not that the app is broken. It is launched once via `openmercato.toml` → `scripts/preview.sh`; a process started before the DevMentor repo replaced the `sandbox-next-seed` scaffold keeps running `next dev` with cwd `/workspace`, where there is no `app/` dir, so Turbopack panics with `ENOENT: scandir '/workspace/app'` and every request 500s. Check `~/.pm2/logs/workspace-preview-error.log`, then `npx pm2 restart workspace-preview`.
- 2026-09-04 — This sandbox force-injects `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/open-mercato` (see `CEZ_ENV_PASSTHROUGH`, which re-injects it into spawned processes, so a plain `unset` in a launcher script does not stick), and `createOrmConfig()` prefers `DATABASE_URL` over the discrete `DB_*` vars. Neither dotenv (`mikro-orm.config.ts` uses plain `loadEnv({ path })`) nor Next overrides a variable already in `process.env`, so the ambient URL silently wins and both the app and every `npm run db:*` command target the wrong database. The CLI still prints `injected env (11) from ../../.env`, which looks like `.env` won; it didn't. Remedies: `.env` now sets `DATABASE_URL` explicitly, `scripts/preview.sh` re-exports `.env` over the inherited environment for the dev server, and one-off CLI runs should be prefixed with `DATABASE_URL=postgres://devmentor:devmentor@127.0.0.1:5432/devmentor` and confirmed with `migration:list`. Do **not** "fix" this with `loadEnv({ override: true })` in `mikro-orm.config.ts`: `tests/integration/environment.ts` passes ephemeral Testcontainers config to child processes through the parent environment, and overriding would break it.
- 2026-09-03 — **`vi.resetModules()` + `await import()` per test is a timeout trap for anything importing `@mikro-orm/*`.** `packages/db/src/config.test.ts` reset the module registry in every case to defeat `getDbEnv`'s module-scope cache, so each test re-imported the entire ORM graph from cold *inside* the test body and blew the 5s default timeout on a loaded machine (2/4 cases failed under CPU contention; the file took 25s). Fix: stub the dependency instead of resetting the registry — `vi.mock('./env', () => ({ getDbEnv: () => current }))` plus one dynamic `import('./config')` at module scope, where no test timeout applies. Per-test time went 25s → 9ms. Reset the registry only when you are genuinely testing module-initialization behavior, and reproduce suspected flakes under `for i in $(seq 8); do (while :; do :; done) & done` rather than trusting a green single run.
- 2026-09-03 — **`.env.example` documents two mutually exclusive connection styles**, so "is this `.env` complete?" cannot be a raw key-set comparison. `DATABASE_URL` is commented out in the example while `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` are live assignments, so `npm run setup` warned that a perfectly good URL-style `.env` was missing five variables — the exact setup the README's "Bring your own PostgreSQL" section tells people to use. Fix: `DATABASE_URL_SUPERSEDES` in `scripts/setup/steps.mjs`, letting a configured URL satisfy the discrete parts it replaces while pool sizing and `DB_DEBUG` stay required. Any new "is it configured?" check has to encode the same precedence the two zod schemas use.
- 2026-09-03 — MikroORM's **seeder glob defaults to `!(*.d).{js,ts}`**, so it imports *every* TS file in `seeder.path` to build its class map. Adding the repo-mandated colocated `database.seeder.test.ts` therefore broke `npm run db:seed` with `TypeError: Cannot read properties of undefined (reading 'config')` — the CLI was importing a Vitest file outside the Vitest runner. Fix: set `seeder.glob: '!(*.d|*.test).{js,ts}'` in `packages/db/src/config.ts`. Watch for the same trap if `migrations` ever gets colocated tests (its default glob is `!(*.d).{js,ts,cjs}`).
- 2026-09-03 — A `spawn()`-based helper must decide whether "command not found" is an *exception* or *data*. In `scripts/setup`, rejecting on the child's `error` event made the installer crash with an ENOENT stack on machines without Docker, bypassing the preflight message written for exactly that case. Missing-optional-tool is a normal outcome: resolve with a sentinel non-zero exit code instead of rejecting.
- 2026-09-02 — In a shared `makeCrudRoute`, don't assume Next always passes `ctx.params`. A **collection** route (`/api/users/route.ts`, non-dynamic) is invoked with no params, so `await ctx.params` is `undefined` and `params[idParam]` throws `Cannot read properties of undefined (reading 'id')`. Guard: `const params = ctx?.params ? await ctx.params : undefined`.
- 2026-09-02 — Services return **DTOs (plain objects), not ORM entities**, across the API boundary. `JSON.stringify` of a MikroORM entity with a bidirectional relation (User 1:1 MentorProfile) risks a cycle; a `toDto()` mapper in the service keeps the envelope clean and gives the route a stable shape. See `.ai/specs/2026-09-01-engineering-standards.md` (SRP).
- 2026-09-02 — The API envelope is a **shape convention, not a shared type**: `@devmentor/core/http` (`ApiResponseBody`) and `@devmentor/ui/backend/api` (`ApiResult`) declare it independently because `ui` must not import `core`. `ui` gained a `zod` dependency so `CrudForm` can take the same schema the server validates with (DRY without importing core).
- 2026-09-01 — MikroORM v7 + Next monorepo gotchas, see [details](lessons/2026-09-01-mikro-orm-v7-next-monorepo.md): (1) v7 has no core decorators — use `defineEntity` + `p` builders; (2) cross-entity relations need per-property thunks (`() => p.oneToOne(X)...`) because `oneToOne` already wraps its arg as `entity: () => target`; (3) register entities as `globalThis` singletons or Next's RSC/SSR/route graphs create duplicate schema instances and `populate` throws `Cannot read properties of undefined (reading 'filter')`; (4) `MikroORM.init()` no longer connects — call `orm.connect()` and don't cache the failed promise; (5) `em.persistAndFlush` removed — use `persist` + `flush`.
- 2026-09-01 — Turbopack does not rewrite `.js`→`.ts` in relative imports the way `tsc` does; use **extensionless** relative imports in TS-source workspace packages (works for tsc/Turbopack/tsx). Symptom was `Module not found: Can't resolve './foo.js'` at build.
- 2026-09-01 — This sandbox exports `NODE_ENV=development` globally, which poisons `next build` (React `_global-error` prerender fails with `useContext` of null). The app's `build`/`start` scripts force `NODE_ENV=production` to compensate.
