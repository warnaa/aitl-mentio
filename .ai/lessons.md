- 2026-11-09 — `npm audit fix` can fail with ERESOLVE on the Storybook/`vite` peer ranges even when the vulnerable packages are unrelated. Do not use `--force`; run `npm update <package>` for fixes inside the declared range, and re-run `npm audit --omit=dev --audit-level=high`.

- 2026-11-08 — **A decision that freezes other data needs that data's writers on the same lock.** Approving a note froze the written answer, but `postAnswer` was a single conditional update that took no booking lock first, so an approval and a replacement could cross. Writers of frozen data now take the booking lock and re-check inside the transaction. Keep that check out of reads that must survive a notes outage: adding it to the session read took down the whole session screen when the notes table was unavailable (NOTES-008). Also: `db:migration:create` still churns unrelated tables, so keep only the changed table in the snapshot and hand-write the migration, and any new `down` step means `NOTES-007`-style tests must run one `db:migrate:down` per migration.

- 2026-11-08 — User correction: make the straightforward workflow correction in the current PR when asked, rather than handing the owner manual GitHub setup instructions for a change the agent can implement and validate.

- 2026-11-08 — Integration child-process environment does not configure the Vitest worker. A CI job selecting mock payments must also set INTEGRATION_TEST_RUN=1 for in-worker createLogger/getEnv calls; keep the flag integration-job-scoped and preserve the production mock-adapter guard.

- 2026-11-08 ? MikroORM forks default to useContext:false, so a separately scoped RateLimiter does not borrow another fork's transaction connection. Consuming its limit inside a booking-locked transaction starves max-one or saturated pools. Preauthorize, consume outside the transaction, then repeat current authorization under a fresh ID-only booking lock; retain real max-one and saturated-pool regressions.

- 2026-11-07 — **An event emitted only on the "first" write loses its side effect for good when that one handler fails.** The written answer first emitted `sessions.answer.posted` only when the stored answer was null, so a failed mentee email could never be retried. Emit on every write and make the consumer idempotent instead: the unique notification row absorbs repeats, and the email is claimed atomically (`nativeUpdate(..., { emailSentAt: null }, { emailSentAt: now })`, only the caller that changed one row sends) and released on failure. Also: `nativeUpdate` bypasses the identity map, so build the response from the input, not the loaded entity.

- 2026-11-03 — **Validate a redirect target *after* normalisation, not only before.** `safeReturnTo` refused a leading `//` on the raw input, then returned the URL parser's normalised path, and dot segments or backslashes (`/foo/..//evil.example`, `/%2e%2e//evil.example`, `/.//evil.example`, `/foo/..\\evil.example`) collapse into `//evil.example`, a protocol-relative off-site URL. The OAuth callback re-validated and so refused it, which is why it was not exploitable yet. Fix: also refuse a normalised pathname starting with `//`, and test that the output is a fixed point (`safeReturnTo(safeReturnTo(x)) === safeReturnTo(x)`).

- 2026-11-03 — **`em.nativeUpdate` bypasses MikroORM's identity map, so the same scope keeps reading the pre-write row; and an incomplete stub row hides it.** `grantRole` then `revokeRole` in one scope: the revoke's `findOne` got the cached entity with the old roles and `sessionVersion`, missed its own precondition and the role stayed. `endAllSessions` twice bumped once. Fix: every version-guarded user write goes through `updateUserAtVersion` (`services/auth/user-version.ts`): conditional `nativeUpdate`, then `em.refresh(user)` (re-hydrates the same instance *and* its `__originalEntityData`, so nothing turns dirty), on a hit and a miss. `user-version.test.ts` pins this on **real** MikroORM with only the driver stubbed. - 2026-11-03 — **A guarded layout keeps deep links only through a `proxy.ts` request header; the proxy is not an auth boundary.** Next gives a layout no pathname and lets its `redirect()` win over the page's, so `/admin/users` signed out used to return to `/admin`. `packages/app/src/proxy.ts` now overwrites `x-devmentor-path` with `pathname + search` on `/admin`, `/home` and `/mentor` (forwarded with `NextResponse.next({ request: { headers } })` — passing `headers` at the top level would send them to the *client*), and the guards read it through `safeReturnTo`, falling back to their literal path. - 2026-11-02 — **A signed token with no random claim is predictable, so the OAuth state cookie check meant nothing.** `TokenService.signPurposeToken` signed only `aud`, `sub`, `iat` and `exp`. Two calls with the same purpose and subject in the same second produced the *same* JWT, so an attacker could call `/api/auth/github` at the moment a victim did, get the exact `state` the victim's cookie held, and pass the callback's equality check with their own GitHub `code` (login CSRF). It came out when a unit test showing "attacker state ≠ victim cookie" was redirected to `/home`. Fix: every purpose token carries `jti: crypto.randomUUID()`, with a regression test that two tokens minted from identical input at the same instant differ. Any token whose *equality* is a security check needs its own entropy; an HMAC over predictable claims gives none.

- 2026-11-02 — **A find-or-create race has a third outcome besides "lost on the unique constraint": the winner commits *between* your lookups.** `UserService.findOrCreateFromGithub` looks up by `github_id`, then by verified email. Against real PostgreSQL (six concurrent first sign-ins), a loser's `github_id` lookup missed, the winner committed, and the email lookup then found a verified row *already carrying this same `github_id`* — which the first draft treated as "linked to another GitHub account" and refused with a 409. The mocked-em unit race passed because its barrier held both callers before the first lookup. Fix: a matching `github_id` on the email branch is the winner, not a conflict; only a *different* id refuses. Verify race handling against a real database (scratch DB, forked ems, a barrier on `flush` to force the constraint path) — a fake em only exercises the interleaving you thought of. Related: an opportunistic write inside `loadSession` uses a conditional `em.nativeUpdate` (precondition `session_version`), never `em.flush()`, because the session resolves lazily mid-service and a flush would commit that service's half-built unit of work.

- 2026-11-02 — **Never cache a rejected promise as a process-wide singleton.** `getContainer` cached `build()`'s promise on `globalThis`, so when the first request hit a down database (`getOrm` rejects) every later request got the same rejection until a restart — the very failure `getOrm` avoids by not caching a failed connection. It now clears the cache when the build rejects (only if the cache still holds that same promise), so concurrent callers still share one in-flight build. A related trap with awilix-scoped async values: a cached `Promise` that a constructor resolves but never awaits becomes an unhandled rejection when it fails, so the scoped `session` attaches a no-op `catch` while awaiters still see the rejection.

- 2026-11-02 — **A PostgreSQL `text[]` in MikroORM v7 is `p.array()` (spiked on 7.1.14).** `p.array()` maps to `ArrayType`, whose Postgres declaration is `text[]` and which hydrates to a real JS `string[]` (`$contains` works); `.default(['mentee'])` emits `default '{mentee}'`, and `p.type('text[]')` is an equivalent spelling. A property-level `.check('…')` is generated as `"<table>_<column>_check"`, recorded in the snapshot, and **lifted by discovery into `meta.checks`** — `meta.properties.roles.check` is `undefined` afterwards, so assert on `checks`. A Postgres `CHECK` passes on `NULL`, so guard array shape with `cardinality(x) > 0` (not `array_ndims`, which is `NULL` for `'{}'`) and reject null members with `array_position(x, null) is null`. Two traps met on the way: the migrations glob has the same colocated-test trap as the seeder glob (now `!(*.d|*.test).{js,ts,cjs}` in `config.ts`), and `config.ts` names the snapshot `devmentor` (→ `migrations/devmentor.json`) while the committed file is `.snapshot-devmentor.json` — run `db:migration:create` with `MIKRO_ORM_MIGRATIONS_SNAPSHOT_NAME=.snapshot-devmentor` (as the integration harness does), or it ignores the committed snapshot, diffs against the live database instead, and writes a stray `devmentor.json`.

- 2026-11-02 — **`npm run test:integration` had never run on Windows; CI is Linux-only, so four POSIX assumptions went unnoticed.** (1) Node refuses to spawn `npm.cmd` without a shell (`EINVAL`, CVE-2024-27980) and deprecates passing an argument array alongside `shell` (DEP0190), so `global-setup.ts` passes one command string on Windows. (4) agent-browser's daemon inherits the CLI's stdout and keeps the pipe open after the CLI exits, so `execFile` hung until its timeout; `runAgentBrowser` writes output to files under `test-results/integration/agent-browser/` and completes on the CLI's exit.

- 2026-11-02 — **A child that kills itself (`process.kill(process.pid)`) exits with code 1 on Windows, not by signal.** Only POSIX reports `code === null` plus a signal, so tests built that way fail on Windows and leave the `code ?? …` branch uncovered. - 2026-09-08 — Three traps found while specifying E02 (`.ai/specs/2026-09-08-mentors-become-bookable.md`) that bite anyone touching roles, slots, or a MikroORM relation before its table exists. (1) **`grantRole` bumps `session_version`, so granting a role signs the caller out unless the route re-issues the cookie.** E01 puts `grantRole` on the closed list of `session_version` triggers; invitation acceptance (#34) is the first grant path, and a handler that commits the transaction without signing a fresh cookie leaves the user's own action invalidating their token — the redirect to `/mentor` then lands on sign-in. Only a route handler can set a cookie in the App Router, so this can never be fixed in a page or a service. (2) **A slot is a bare start instant but the *mentee* picks 25 or 50 minutes at booking (#36 + #40), so slots at 14:00 and 14:30 can double-book a mentor** — neither issue notices. The read-time filter is `viableLengths(slotStart, occupied, lengths)`; the guarantee is *not* a per-slot lock, which two concurrent bookings on two different slots sail straight through. Serialise on the **mentor** row (`SELECT … FOR UPDATE` on `mentor_profiles`) and back it with `EXCLUDE USING gist (mentor_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` on `bookings`. (3) **Never declare a MikroORM relation whose column does not exist yet.** A `Slot.booking` property with no `booking_id` column puts the column in every generated `SELECT` (so all reads of `slots` fail) and regenerates it on the next `db:migration:create` diff against the committed snapshot. Also note two boundaries that block the obvious implementation: `packages/db/**` may not import `@devmentor/core` (`eslint.config.mjs:44-48`), so a migration cannot call a vocabulary's `sqlValueList()` or a `uniqueSlug()` helper — hand-write the SQL and guard the drift with a `core`-side test that reads the migration file; and `SDLC.md:97` grades **any** schema migration `risk-high`, however small the feature.

- 2026-09-04 — An OAuth **state** cookie must be `SameSite=Lax`, never `Strict`.
